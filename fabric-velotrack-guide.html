Watch a fleet live, score its risk, and let an agent answer for it

Follow along and you will build a working live-logistics platform: an Eventstream landing GPS and scan events, an entire Silver+Gold transformation layer built from eight declarative views instead of Spark notebooks, a leakage-controlled model scoring every shipment's late-delivery risk, and an Ontology-bound agent answering ops questions from the same tables the report reads. No prior Fabric experience assumed, and nothing to buy.

Why anyone builds this

VeloTrack is a parcel-logistics operator: it owns the vehicles and the depots, not the warehouse the parcel started in. Three things go wrong constantly, and all three are usually found too late to do anything about them.

The problemHow it usually gets found
A route quietly running late all dayThe next-morning ops report
A depot backing upA driver calling in, hours into the shift
A shipment that is going to miss its promiseThe customer's own tracking page, before anyone internal knows
And the part most demos skip: a live dashboard that only shows what already happened is just a faster version of the next-morning report. This platform scores every active shipment's late-delivery risk before it is late, on a model that was never allowed to see the labels it is trying to predict — and an agent answers plain-English ops questions from the same graded tables, not a separate copy.

1

Set up the workspace, capacity and Git — before you build anything

about 30 min

Everything lives in one Fabric workspace attached to a trial capacity, with Git integration connected from the very start.

  1. Sign in at app.fabric.microsoft.com with your work or school account and start (or confirm) your Fabric trial.
  2. Workspaces → New workspace. Call it something like VeloTrack-Dev, and under Advanced set the licence mode to your trial capacity.
  3. On GitHub, create a new, private repository for the raw estate — this project used velotrack-fabric-estate — initialised with a README (Fabric will not connect to a repo with zero branches), then create a working branch off main.
  4. Workspace settings → Git integration → connect it to that repository, that branch, and a subfolder (not the repo root) so notebooks and docs can live beside the synced item definitions without Fabric trying to manage them too.
Why a private estate repo, separate from this public one? Fabric Git integration syncs raw item definitions — workspace GUIDs, capacity ids, connection strings. This public repository is a scrubbed, curated subset, built by a publish step, never synced straight out of the workspace. Two repos, two jobs: one Fabric writes to continuously, one a human curates once.
A Fabric trial needs a work or school account. A personal Microsoft account cannot activate one. If you do not have one, that is step zero, and there is nothing to debug.
Read the trial banner every session, not just once. This build's own contract had to be revised after its first expiry reading turned out to be one day optimistic — the trial API does not return an expiry field, so the banner is the only source of truth and it must be re-read.
Git integration can silently refuse to connect from inside a coding-agent session
If a browser-automation-driven session tries to click through the connect dialog itself, it may simply never land — this project tried three times from three different automated channels before connecting it by hand, in the portal, in about four minutes. When an automated path stalls twice on the same step, stop and do it by hand rather than trying a fourth channel.
2

Generate the fleet, the shipments, and the events

about 2–3 h

A logistics platform needs shipments moving. This build generates its own: about 120 vehicles across 8 depots and 15 routes, 25,000 shipments over a 30-day window, and roughly 3.4 million GPS pings replayed to look live.

Why generate rather than download a dataset? The point of this build is scoring late-delivery risk, and you cannot grade a risk model without knowing which shipments were genuinely going to be late and why. The generator plants known route-congestion windows and depot-backlog days — the injected truth — and that register is the answer key the scoring model is measured against, never trained to see directly.

Clone the repo (see Get the code), then:

pip install -r notebooks/requirements.txt   # if present — else see GENERATOR_SPEC.md §8
python -m generator.run --seed <your-seed> --out ./output

The generator's dirty-data layer is deliberate: duplicate scan events and out-of-order GPS pings, so the transformation layer's dedupe and ordering logic is real work, not decoration.

A generator can pass every unit check offline and still be wrong in aggregate
Episode attribution — the fraction of injected late-delivery episodes the generator's own labels correctly attribute — measured at 9.7%/90.3% against a 65–75%/25–35% target on the first dev-scale run: the near-inverse of the design intent, even though every smaller unit check passed. A 54-configuration sweep recalibrated the injection intensity — never the late-delivery threshold, which stays fixed by the project's own standing rule — and closed the gap to 72.5%.
Seed it, version it, and prove it byte-reproducible. Run the generator twice into different folders and diff them. If a fixed seed does not reproduce the same output, every number you publish later is unreproducible.
3

Create the Eventstream and the Bronze lakehouse

about 1–2 h

An Eventstream takes the GPS-ping and depot-scan feed and lands it, live, in a Lakehouse — this build's LH_VeloTrack.

  1. New item → Eventstream. One stream, multiplexing GPS pings and scan events.
  2. New item → Lakehouse, schema-enabled, with a bronze schema created explicitly before the first load — Fabric does not create it for you on an empty rebuild.
  3. Point the Eventstream's destination at the Lakehouse and start it; then run the backfill notebook for history.
Live-replay events can post cleanly and never reach Bronze. On this build, 324,854 replayed events were confirmed received and forwarded by the Eventstream's own monitor, and Bronze still showed backfill-only counts. Four independent checks pointed at a gap inside the Eventstream→Lakehouse write path itself — not a generator bug, not a query bug. It was never root-caused. If your own rebuild hits the same wall, reconcile against the stream's own delivery metrics and a direct table count before trusting either alone.
Rebuild-from-empty needs the Bronze schema created explicitly. A notebook that assumes the schema already exists will fail silently informative or not at all on a truly empty Lakehouse.
4

Build the transformation layer as Materialized Lake Views — no orchestrated Spark ETL

about 2–3 h

This is the step that makes the build different. Instead of Bronze→Silver→Gold notebooks, the transformation is declarative SQL: CREATE MATERIALIZED VIEW ... AS SELECT, maintained by the engine.

  1. Author the view definitions in one file, in dependency order — Silver views first (dedupe, ordering), then Gold (the shipment/route/depot feature tables the model and the scoring notebook both read).
  2. Deploy and confirm: 8 views, 3 Silver + 5 Gold, all live on the first full run.
An MLV is a tagged Delta table, not a naming convention
Fabric rewrites the stored view definition to a default.-prefixed four-part name on save. Count views by their xCatalogTableType = MATERIALIZED_LAKE_VIEW tag, never by what you named them — the name you gave a view is not reliably what comes back on read-back.
A probe's own verdict can be the defect, not the capability
This project's first MLV availability probe returned a hard FAIL — and the capability was fine. The probe's own SQL had a bug. A second probe with a negative control (deliberately reproducing the first probe's exact error on demand) proved the failure was in the test, not the platform, before a single hour of build time was spent working around a constraint that did not exist.
A hand-typed deploy payload above roughly 8 KB corrupts silently. This project found the same corruption class four separate times across its life — non-ASCII-safe substitutions inside valid base64 (b→r, +→-, 2→z) that a naive scan would miss entirely. Author definitions to a file and deploy through a file-based channel; never hand-transcribe a payload of any real size through a chat-style tool call.
5

Score late-delivery risk — leakage-controlled, cohorted

about 3–4 h

One notebook reads the Gold shipment-features table, trains on a strict split, and writes gold.shipment_risk_scores — one row per shipment, a risk score and a band.

Why the split has to be enforced before any feature is read, not after. The generator's injected late-delivery episodes are the whole point of the story — and also the easiest thing in the build to leak into the model by accident. If a feature derived from the same window used to label an episode reaches the training set, the model will look excellent and mean nothing.
Code that has never executed anywhere needs to meet a fake of the interface it touches first
This project's scoring notebook crashed on its first real tenant run — ValueError: Input X contains NaN — from a COALESCE inconsistency in the MLV layer that a fake-Spark test harness would have caught in minutes. It did catch it, the second time it was tried: a small harness that fakes the ONE interface a notebook cell touches is cheap to write and finds real defects before the tenant does. See tests/fake_spark.py in this repository.
A wrong hypothesis, floated and then corrected, is worth keeping in the record. "Class imbalance in the stratified split" was the first guess for the crash above. The real cause was found only once the actual traceback was read — not inferred from symptoms.
6

Build the Direct Lake semantic model — measures via XMLA, never portal-typed

about 2 h

Four Direct Lake tables read the Gold schema directly: no import, no refresh, no Gold-beneath-Gold layer. Every measure is added over XMLA/TOM after the shell is created — never typed by hand in the portal, so the model itself is the source of truth and can be pulled back out as .tmdl on demand (see model/ in this repository).

gold.shipment_features        -> shipment_features   (12 measures)
gold.route_performance         -> route_performance    (4 measures)
gold.depot_throughput          -> depot_throughput     (3 measures)
gold.shipment_risk_scores      -> shipment_risk_scores  (9 measures)
A brand-new Direct Lake connection can time out on its first several attempts
One session hit ConnectFabric failing 7 of 7 times, roughly 60 seconds each — about half an hour lost before the shell finally connected. If this happens to you, it is very likely transient service-side state, not a configuration mistake; keep the retry loop tight and move on to other work if it needs a session boundary to clear.
Validate on both routes. Every measure's definition should be read back against a rendered value, and the model should pass both this engine's own linter and the official powerbi-report-author validate CLI at 0 errors before you build the report on top.
7

Bind the Ontology, stand up the agent layer, and build the report

about 3–4 h

An Ontology binds entity types to the live Gold schema; an agent — originally planned as a Data Agent — answers scripted ops questions grounded in the same model; a five-page Power BI report (four content pages plus an auto-generated guide page) reads the model directly.

Check whether your component is actually available on your capacity SKU before you build around it — with a control, not an assumption. This project's Data Agent was killed outright: UnsupportedCapacitySKU: FTL64 SKU Not Supported, confirmed against a working item type (AISkill returned a different, generic error) so the failure could be pinned on the SKU specifically rather than guessed at. An OperationsAgent substituted in the same session, at zero build cost, because the kill criterion had been written down before the build started.
Test a platform-gate explanation before you write it down. This project initially reasoned that the OperationsAgent's own blockers were "gated by trial capacity" — the easier, more forgiving explanation. Pushed to actually test that claim, it turned out false: the real cause was an unbound knowledge source, a build gap, not a platform limit. Self-correcting inside the same session it was written is the discipline worth copying, not the first draft of the explanation.
8

Deploy from Git, verify by query, and publish

about 1–2 h

The estate's job in this project is to prove itself as its own CI/CD demo: item definitions on disk, deployed from the Git-integrated folder, verified by querying the live service rather than by reading a screenshot.

  1. Commit every item definition to the estate's Git branch as you build it — not as a batch at the end.
  2. Deploy via whichever channel actually reaches your tenant. This build's intended channel (deploy_items.py / fab, via az login) needs outbound network access from wherever you run it; if that access is not available, Fabric Core MCP is the fallback, with definitions kept small enough to deploy inline (see the ~8 KB warning in step 4).
  3. Verify every claim by query: item counts via list_items, row counts via a direct query against the Lakehouse or the model, never by re-reading a portal screenshot for a number a query would answer.
State plainly which deployment route you actually used. This project's own central question was whether a fully offline deploy-then-verify loop is faster than doing the same build by hand — and it could not answer that question, because its intended channel was never reachable from any session's tooling. Every item here was deployed through Fabric Core MCP instead. Naming that plainly is worth more than letting a portfolio piece imply a channel it never actually used.
Publish the report through whichever channel is safe for its size. A full PBIR definition can run into the hundreds of kilobytes of base64 — well past the point a hand-transcribed MCP call should carry it. A Desktop publish (File → Publish) is a legitimate fallback on the engine's own cheapest-route ladder, not a failure of automation, as long as the result is then verified independently — list_items/get_item against the workspace, not trusted on say-so.

What this build does not do

Stated plainly, so nothing here oversells itself. A reviewer would find all of these in ten minutes; it is cheaper to say them.

  • The live-replay leg of the Eventstream→Bronze path was never reconciled. 324,854 events posted cleanly, the Eventstream's own monitor confirmed receipt and forward, and Bronze never showed them. Four independent checks pointed at the write path itself; none diagnosed it. Recorded as an open defect, not reinterpreted as a pass.
  • The OperationsAgent's Generate playbook action fails reproducibly (3/3) for an undiagnosed reason. The 5 scripted ops questions it was meant to answer ARE answered correctly — DAX-verified against the model directly — but the agent action itself does not work, and the agent-config surface is opaque to every capture tool this project had.
  • The real-tenant model AUC was never retrieved. Only an offline proxy (0.9763) is documented.
  • The project's own central question could not be answered. Whether authoring definitions offline and deploying via a file-based channel is actually faster than the previous project's build — the channel that question depends on was never reachable from any session's tooling, so the question was never actually tested, only asked.
  • The data is invented. VeloTrack Logistics is fictional. The shape is realistic; no figure represents a real fleet, shipment, driver or depot, and every injected element — including the late-delivery episodes used to test the scoring model — is declared in GENERATOR_SPEC.md.
  • Trial capacity only, on a 20-day Fabric trial. Nothing here says what this would cost to run in production.
If you build this and get further than I did — particularly on the live-replay write path, or the Generate playbook failure — I would genuinely like to hear about it.
